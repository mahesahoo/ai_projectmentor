# AI Academic Project Mentor

An agentic platform that turns a student's rough project idea into a full academic
project blueprint — feasibility, scope, tech stack, timeline, and risks — then keeps
mentoring through execution via chat, progress-driven replanning, and on-demand
documentation, with a faculty dashboard giving mentors a health-at-a-glance view
across every student. Milestones 1–4 complete (see status sections below) — this
is the finished project.

## Stack
- **Backend:** FastAPI (Python)
- **Frontend:** plain HTML/CSS/vanilla JS (no build step)
- **Database:** SQLAlchemy ORM → SQLite by default, PostgreSQL-ready
- **Auth:** JWT (24-hour expiry)

## Setup

```bash
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

## Run

```bash
uvicorn app.main:app --reload
```

Open **http://localhost:8000** — this serves both the frontend pages and the API
from the same process (no CORS issues, no separate frontend server).

- `/` → landing page
- `/register.html` → create account
- `/login.html` → log in
- `/profile.html` → view/edit profile, log out
- `/skill_assessment.html` → rate proficiency per tech stack
- `/docs` → interactive API docs (Swagger UI, auto-generated by FastAPI)

## Agent pipeline setup (Milestone 2 + 3 + 4)

Every agent — Feasibility, Scope, Tech, Timeline, Risk (the blueprint pipeline),
the conversational Mentor, Replan, and Documentation agents (Milestone 3), and
the Faculty Summary agent (Milestone 4) — calls the Gemini API (`gemini-3.5-flash`,
on Gemini's free tier) and needs a key set before running the app. Get a free key
at https://aistudio.google.com/apikey, then:

```bash
export GEMINI_API_KEY="..."
uvicorn app.main:app --reload
```

Never commit the key — it's read from the environment only, same convention as
`DATABASE_URL` below. The app boots fine without this set (Milestone 1 routes
don't need it); only idea submission's background pipeline and the synchronous
M3/M4 endpoints (chat/replan/documents/faculty-summary) need the key, and fail
gracefully if it's missing or the upstream API errors (pipeline sets
`idea.status` -> `"failed"`; the synchronous endpoints return a clean `503`
with a friendly message instead of hanging or throwing a bare `500`).

The Gemini SDK is configured with **no automatic retry** (confirmed by tracing
`google-genai`'s own retry logic — see `infos/MILESTONE4_CHECKLIST.md` step 17):
a deliberate choice, since `429` (free-tier quota exhaustion) is retriable per
the SDK's own defaults but can't actually succeed on retry, and this app's own
free-tier key does hit that limit (20 requests/day/model) during heavy testing.
Failing fast with a clean error is better than a silent multi-second retry that
ends in the same failure.

## Switching to PostgreSQL

No code changes needed. Just set an environment variable before running:

```bash
export DATABASE_URL="postgresql://user:password@localhost:5432/project_mentor"
pip install psycopg2-binary   # Postgres driver, not needed for SQLite
uvicorn app.main:app --reload
```

## API endpoints

| Method | Path | Auth | Purpose |
|---|---|---|---|
| POST | `/api/auth/register` | No | Create a student account |
| POST | `/api/auth/login` | No | Get a JWT access token |
| GET | `/api/profile/me` | Yes | Get your profile |
| PUT | `/api/profile/me` | Yes | Update name/branch/year |
| POST | `/api/profile/me/skills` | Yes | Add a skill assessment rating |
| GET | `/api/profile/me/skills` | Yes | List your skill assessments |
| POST | `/api/ideas` | Yes | Submit a project idea (status defaults to "submitted"), triggers the agent pipeline in the background |
| GET | `/api/ideas` | Yes | List your submitted ideas |
| GET | `/api/ideas/{idea_id}` | Yes | Get one of your ideas |
| GET | `/api/ideas/{idea_id}/blueprint` | Yes | Aggregated feasibility + scope + tech + timeline + risk (latest of each) |
| GET | `/api/ideas/{idea_id}/chat` | Yes | Full mentor conversation history |
| POST | `/api/ideas/{idea_id}/chat` | Yes | Send a message, get a reply grounded in the finished blueprint (requires `status == "analyzed"`) |
| GET | `/api/ideas/{idea_id}/progress` | Yes | Logged progress-update history |
| POST | `/api/ideas/{idea_id}/progress` | Yes | Log a progress update (no LLM call) |
| POST | `/api/ideas/{idea_id}/replan` | Yes | Re-run Timeline + Risk agents with progress history as context; persists new rows, keeps old ones |
| GET | `/api/ideas/{idea_id}/documents` | Yes | All generated documents, most recent first |
| POST | `/api/ideas/{idea_id}/documents` | Yes | Generate a document on demand (`doc_type`: `synopsis` \| `methodology` \| `progress_report`) |
| GET | `/api/faculty/dashboard` | Faculty only | Every student's every idea, with computed health indicators + latest generated summary |
| POST | `/api/faculty/ideas/{idea_id}/summary` | Faculty only | Generate (or regenerate) that idea's AI summary + health status — explicit action, not automatic |
| GET | `/api/faculty/ideas/{idea_id}` | Faculty only | Single-idea drill-down: full blueprint + progress log + chat history + latest summary |

There's no faculty registration flow — `Student.is_faculty` is a plain boolean,
flipped manually via the DB for a demo account (see `infos/MILESTONE4_CHECKLIST.md`'s
"Faculty access" decision: a full second account type would be scope creep for
what the brief actually asks for). Faculty routes are gated by a
`get_current_faculty` dependency that wraps the same JWT auth every other route
uses, not a separate login system.

## Running tests

```bash
pip install -r requirements.txt   # pulls in pytest + httpx (M4)
pytest                             # 25 tests, ~7s, no GEMINI_API_KEY needed
pytest -m live                     # + the 1 test against the real Gemini API
```

The default run mocks every `run_*_agent` call at the module boundary each caller
actually imports from, so it's fast and deterministic and never touches the real
`project_mentor.db` (`tests/conftest.py` points `DATABASE_URL` at a throwaway file
before any app module is imported — see the comment there for why a plain FastAPI
`dependency_overrides` patch alone wouldn't have been enough, given the pipeline's
`BackgroundTask` builds its own DB session directly). `pytest -m live` additionally
runs one real end-to-end submission against Gemini; it's skipped by default since it
needs a working key and costs real quota. This formalizes what Milestones 1-3 had
only validated manually (registration, duplicate-email rejection, login, wrong-
password rejection, auth-required routes, idea submission/isolation, the not-feasible
early-stop, chat/replan/documents gating and persistence, and the faculty dashboard's
auth gating, aggregation, and health-indicator computation).

## Milestone 2 status

All five tasks complete:
- Task 1 — Feasibility Analysis Agent (`app/agents/feasibility.py`)
- Task 2 — Scope Definition Agent (`app/agents/scope.py`)
- Task 3 — Technology Recommendation Agent (`app/agents/tech.py`) — the one
  agent that actually consumes Milestone 1's `SkillAssessment` data, weighting
  stack choices toward technologies the student already knows
- Task 4 — Timeline Planning Agent (`app/agents/timeline.py`)
- Task 5 — Validation, run against 4 varied sample ideas (solid, vague,
  overambitious, and a skill-weighting check) via the real Gemini API

Pipeline: `app/agents/pipeline.py::run_pipeline` chains the four agents,
persisting each stage's output and advancing `idea.status` through
`analyzing_feasibility -> analyzing_scope -> analyzing_tech ->
analyzing_timeline -> analyzed`. A `"not_feasible"` verdict stops the
pipeline right after the Feasibility stage rather than forcing the later
agents to scope/plan a project the student never actually proposed. Any
failure (Gemini API error, missing key, etc.) sets `status = "failed"`.
Fetch the aggregated result via `GET /api/ideas/{id}/blueprint`.

## Milestone 3 status

All four tasks complete:
- Task 1 — Risk Assessment and Mitigation Agent (`app/agents/risk.py`) — the
  5th and final stage of the blueprint pipeline (`analyzing_timeline ->
  analyzing_risk -> analyzed`), reads the full scope/tech/timeline and flags
  concrete, project-specific risks with likelihood + mitigation.
- Task 2 — Conversational Mentor (`app/agents/mentor.py`,
  `GET/POST /api/ideas/{id}/chat`) — plain-text, multi-turn chat grounded in
  the finished blueprint, using Gemini's native chat `Content`/`Part` format
  for real conversation memory. Synchronous (immediate reply), not a
  background task like the pipeline. Gated on `status == "analyzed"`.
- Task 3 — Progress tracking + replan (`ProgressUpdate` model,
  `app/agents/replan.py`, `GET/POST /api/ideas/{id}/progress`,
  `POST /api/ideas/{id}/replan`) — logging progress is a free DB write;
  replanning (re-running Timeline + Risk with the progress history as
  context) is a separate, explicit, costly action so a chatty student can't
  accidentally trigger repeated agent runs. New `TimelinePlan`/
  `RiskAssessment` rows are added, not overwritten — old plans stay in the
  DB as an audit trail.
- Task 4 — On-demand documentation generation (`app/agents/docs.py`,
  `GET/POST /api/ideas/{id}/documents`) — synopsis, methodology, and
  progress-report generation as persisted Markdown, generated only when
  requested (never automatically), each persisted as a new row.

**Design decision:** the brief describes progress updates as triggering plan
adjustments "via the agent pipeline." This build keeps logging progress and
triggering a replan as two separate actions rather than auto-replanning on
every log entry, to keep API cost predictable — a deliberate, documented
deviation from the brief's literal wording (see `infos/MILESTONE3_CHECKLIST.md`).

**Validated end-to-end** (`infos/MILESTONE3_CHECKLIST.md` task 21): a full
continuous walkthrough on one idea — pipeline through all 5 agents, 2-turn
chat with confirmed memory and grounding, 2 progress logs followed by a
replan (confirmed the timeline actually changed and old/new rows both
persisted), and all 3 document types (confirmed the progress report refuses
to fabricate progress that wasn't logged) — plus an edge-case run on a
deliberately vague/infeasible idea confirming chat and document generation
degrade gracefully with no scope/tech/timeline/risk, while `replan` correctly
returns `409` since there's nothing to replan. 37/38 automated checks passed
(the one failure was a wrong URL in the test script itself, not an app bug).

## Milestone 4 status

All four tasks complete — this is the final milestone (see `infos/mil4.jpeg`):

- Task 1 — Faculty monitoring dashboard (`app/agents/faculty_summary.py`,
  `app/routers/faculty.py`, `GET /api/faculty/dashboard`,
  `POST /api/faculty/ideas/{id}/summary`, `GET /api/faculty/ideas/{id}`) — a
  9th agent synthesizes each project's full trajectory (blueprint + progress
  + chat + replan history) into a short faculty-readable summary plus a
  `health_status` tag (`on_track` / `at_risk` / `stalled` / `not_feasible`),
  generated on demand like every other costly action in this app. The
  underlying health *indicators* (weeks completed, high-risk count, replan
  count, days since last update, chat engagement) are computed directly from
  existing tables with zero LLM calls — only the natural-language summary
  itself is generated. `weeks_completed` is derived from
  `ProgressUpdate.week_number`, not parsed out of the timeline's task text
  (an earlier design draft tried that; it silently returns 0 for any project
  that hasn't replanned yet, since the "Completed:" wording is prose the
  replan agent happens to write, not a structured field).
- Task 2 — End-to-end automated testing (`tests/`, `pytest.ini`) — see
  "Running tests" above. 25 mocked tests plus 1 real one against the live
  Gemini API.
- Task 3 — Prompt/pipeline reliability pass (`infos/MILESTONE4_CHECKLIST.md`
  steps 16-18): fixed a token-budget bug where `gemini-3.5-flash`'s internal
  "thinking" tokens were truncating structured JSON output on the two
  tightest agents (`faculty_summary.py`, `mentor.py`); normalized agent
  naming for consistency; traced `google-genai`'s retry logic and confirmed
  the SDK retries nothing by default (a wrong assumption this checklist had
  briefly carried from M3 — corrected before it could reach this README).
- Task 4 — Final documentation, project report, and demonstration — this
  README section, `PROJECT_REPORT.md`, `Milestone4_Presentation.pptx`, and
  `PRESENTATION_SCRIPT_M4.md`.

**Design decision:** the brief describes faculty summaries as "auto-generated."
This build makes summary generation an explicit, on-demand action instead —
the same cost-discipline reasoning as M3's replan: a faculty member browsing
many projects shouldn't silently trigger an LLM call for every row just by
loading the dashboard. A deliberate, documented deviation from the brief's
literal wording, not an oversight.

**Design decision:** faculty access is a plain `is_faculty` boolean on the
existing `Student` model plus a `get_current_faculty` auth dependency, not a
separate faculty account/registration system. The brief asks for a "faculty
monitoring dashboard," not a second user type with its own signup flow —
building one would be real scope creep for a milestone budgeted at ~10 hours,
and reusing the existing JWT auth means the faculty routes get the exact same
security properties (expiry, hashing, etc.) for free.

**Design decision:** no automatic retry on Gemini API failures. Traced
`google-genai`'s retry configuration directly and confirmed `genai.Client()`
with no explicit `http_options` retries nothing (`stop_after_attempt(1)`) —
every call either succeeds on the first attempt or fails immediately. Adding
retry was considered and declined: `429` (free-tier daily quota exhaustion,
this project's actual dominant failure mode during heavy testing) is in the
SDK's own retriable-status list, but retrying a quota-exhausted call cannot
succeed — it would just add several seconds of silent delay before an
identical failure, which is strictly worse for a live demo than the fast,
clean `503` this build already returns (see `app/routers/ideas.py`'s
`_call_agent` helper, added in M3/M4 work).

**Validated end-to-end**: the full faculty flow (multi-student dashboard
aggregation, summary generation + persistence + audit trail across repeated
generations, health-indicator correctness against known fixture data, auth
gating for both non-faculty students and unauthenticated requests, and the
404/409 edge cases) was run against a real running server with real Gemini
calls, not just the automated suite's mocks — see `infos/MILESTONE4_CHECKLIST.md`
for the full validation log, including two real bugs this live verification
caught that the structural review alone had missed (the token-budget
truncation, and a missing `status === "failed"` guard in the faculty detail
view's frontend rendering).
